# 리뷰어별 실행 가능 검증 계획

## 1. 목적과 주장 경계

본 계획은 현재 구현과 실험 자료를 리뷰어의 지적과 일대일로 연결하는 사전등록용 실행 계획이다. 기존 128건의 저자 구축 정답과 235건의 완전 익명 다중 AI 판정은 탐색 결과로 보존하되, 독립 인간 정답을 대체하지 않는다. 주 성능 주장은 정답 동결, 임계값 동결 및 블라인드 테스트 동결 후에만 산출한다.

## 2. 현재 완료 및 미완료 현황

## 3. 공통 실험 계약

모든 실험은 실행 전에 Git commit, 룰 카탈로그 해시, 지침 코퍼스 해시, L1 스냅샷 ID, 모델명, 프롬프트 해시, temperature, seed, API 가격표 조회 시점과 실행 환경을 동결한다. 파일·함수·파생 소스를 `group_id` 단위로 묶으며, 같은 그룹을 개별 occurrence로 분할하지 않는다. 반복 실행의 동일 응답은 새 표본으로 계수하지 않는다. 핵심 비율은 `group_id` cluster bootstrap 10,000회의 95% 신뢰구간과 같이 보고한다.

## 4. 독립 인간 occurrence GT

### 4.1 데이터와 표본수

주 판독 표본은 최신 유효 스냅샷 265건 전체와 추가 일반화 코퍼스의 L1 occurrence로 구성한다. 273건은 누출 제거 직후의 역사적 중간 스냅샷으로만 보존하고 새 성능 분모로 사용하지 않는다. 외부 암호모듈 전문가 2명이 서로의 판정과 시스템 출력을 보지 않고 265건을 전수 판정한다. 불일치와 한 명이라도 `insufficient_context`로 판정한 항목은 제3의 인간 전문가가 재심한다. 만약 인력 제약으로 일부만 시작한다면 265건 중 임의 소표본을 만들지 않고, 우선 265건을 하나의 완결된 LEA 층으로 끝낸다.

라벨은 `violation`, `non_violation`, `insufficient_context`, `not_applicable`로 폐쇄한다. 적용성, 근거 행, 판정 사유, 출처 인용과 확신도를 필수로 한다. 함수명, API명, 파일명과 추적성은 보존하되, 저자가 삽입한 정답 표지만 제거한 `minimal_cue_controlled` view를 인간 GT의 주 view로 사용한다.

### 4.2 분할·통계·수용 기준

- GT 작성 단계에서 train/development/test 분할을 사용하지 않는다. 정답 동결 후 `group_id`를 기준으로 development 40%, test 60%를 층화 분할하며, test는 최종 평가 전까지 봉인한다.
- 1차 지표는 4분류 Cohen's κ와 정확 일치율이다. 라벨별 one-vs-rest κ와 불일치 유형도 보고한다.
- 수용 게이트는 전수 이중 판독 100%, 필수 필드 누락 0건, 결측·중복 occurrence 0건, 정확 일치율 80% 이상 및 κ 0.60 이상으로 정한다. κ가 0.60 미만이면 지침 보완 후 동일 인원이 실패 항목을 서로 협의하지 않고 재판독한다. 게이트를 통과하지 못한 라벨은 주 GT로 사용하지 않는다.
- 조정 후 `violation/non_violation`을 확정한 occurrence만 주 성능 분모에 포함한다. `insufficient_context`와 `not_applicable`는 탈락시키지 않고 coverage 및 abstention 지표로 별도 보고한다.

### 4.3 산출물

공개 패킷, 라벨러별 불변 JSON, 일치도 보고서, 조정 큐, 조정된 GT, `group_id` 분할 manifest, SHA-256 원장, 라벨러 자격과 이해관계 선언서를 보존한다.

## 5. 3-view 최소 블라인드 실험

### 5.1 데이터와 분할

동일 occurrence ID를 공유하는 다음 세 view를 최신 유효 스냅샷 265건 전체에 생성한다.

1. `analysis_artifact_aware`는 일반 명칭과 의미 있는 주석을 보존하고 직접 정답 주석만 제거한다.
2. `minimal_cue_controlled`는 생성 provenance로 확인된 정답 표지만 제거하고 정상 함수명·API명·파일명을 보존한다.
3. `fully_opaque`는 명칭 의존성 스트레스 테스트이며 주 성능 평가에 사용하지 않는다.

명칭 자체가 요구사항인 규칙은 명칭을 전 view에 보존하거나 opaque 비교의 분모에서 제외한다. 이 예외는 원문 페이지·문구·적용 범위를 provenance catalog에 사전 기록한 경우에만 허용한다. 인간 GT는 `minimal_cue_controlled` view에서 한 번만 확정하고, 시스템은 세 view를 모두 판정한다. 이로써 라벨러가 같은 occurrence를 반복해 보고 정답을 기억하는 오염을 피한다.

### 5.2 통계와 수용 기준

- 주 비교는 artifact-aware 대 minimal view의 occurrence 단위 판정 변화이며 paired McNemar exact test와 `group_id` paired bootstrap 95% 신뢰구간을 사용한다.
- minimal 대 opaque는 명칭 제거에 따른 성능 변화, abstention 증가와 규칙별 flip 비율을 보고하는 부가 분석이다.
- 각 view의 precision, recall, F1, specificity, coverage와 confusion matrix를 같은 동결 GT로 산출한다.
- 수용 게이트는 occurrence 결합 100%, 중복·누락 0건, 동일 문맥에서 표시하는 line range 일치 100% 및 공개 패킷의 정답·L3·신뢰도·로컬 경로 누출 0건으로 정한다. 성능 차이에 대한 인위적 수용 한계는 사후에 설정하지 않고, 차이와 신뢰구간을 그대로 보고한다.

### 5.3 산출물

3개 패킷과 sealed join sidecar, generator provenance manifest, 누출 감사서, view별 판정 원장, paired transition matrix, 규칙별 효과크기 및 bootstrap 분포를 생성한다.

## 6. L2 RAG 독립 기여도

### 6.1 데이터·분할·실행

인간 GT와 결합된 동결 L1 전체를 사용한다. development에서 prompt와 retrieval 설정을 고정하고 test를 단 한 번 개봉한다. RAG과 no-RAG에서 L1 후보, 모델, system/user prompt 본문, 출력 계약, temperature와 재판정 정책을 같게 유지하고, 검색 문맥 주입만 변경한다. 조건 순서를 AB/BA로 교차하며 응답 cache를 조건 간 공유하지 않는다.

모델이 temperature 0에서 결정론적인 경우 표본수는 고유 occurrence 수이지 반복 횟수가 아니다. API 일시 오류 및 순서 효과 감사를 위해 AB/BA 3쌍은 유지하되, 성능 통계는 동일 응답을 반복 계수하지 않는다.

### 6.2 통계와 수용 기준

- 주 지표는 정답률, precision, recall, F1, coverage의 paired 차이이다. RAG만 맞은 수와 no-RAG만 맞은 수에 McNemar exact test를 적용한다.
- `group_id` paired bootstrap 10,000회로 F1·recall·precision 차이의 95% 신뢰구간을 산출한다. 규칙별 결과는 표본수와 함께 탐색적으로 보고한다.
- 증거 적합성은 test occurrence의 20% 또는 최소 50건 중 더 큰 표본을 임의 추출하여, 독립 전문가 2명이 `supports`, `irrelevant`, `contradicts`, `insufficient`로 평가한다.
- 무결성 게이트는 조건별 L1 ID 집합 일치 100%, no-RAG의 retrieval 호출·문맥·evidence 0건, prompt 해시의 예정된 필드 외 일치 100%, 요청 성공률 100% 및 raw occurrence 없이 집계가 재생성되는 것으로 정한다.
- RAG 우월성은 결과를 보고한 뒤에 정한 기준으로 선언하지 않는다. 사전에 고정하려면 적어도 test recall을 감소시키지 않고, F1 차이의 95% 신뢰구간 하한이 0을 초과하며, 증거 `supports` 비율이 유의하게 높은 경우로 정한다. 통과하지 못하면 독립 기여도를 주장하지 않는다.

### 6.3 산출물

동결 L1 manifest, AB/BA 실행 원장, retrieval 결과 해시, prompt·response 해시, candidate-level paired 표, McNemar 결과, bootstrap 분포, 증거 적합성 라벨과 조정 기록을 보존한다.

## 7. AES·SEED·ARIA 일반화 평가

### 7.1 데이터와 표본수

기존 28건 KAT는 선택한 구현체의 빌드·실행 검증으로 유지하고 탐지 성능 표본으로 계수하지 않는다. 탐지 평가는 알고리즘별로 적어도 두 개의 서로 다른 신뢰 구현체를 사용한다. 1차 코퍼스 구축 목표는 알고리즘별 120 occurrence와 평가 가능한 양성·음성 각 40건으로 정하되, 이 수를 검정력 근거 없는 고정 최소치로 해석하지 않는다. 초기 코퍼스의 실증 양성률, `group_id` 수, 효과크기와 클러스터 내 상관을 사용해 사전 검정력 분석을 수행한 뒤 필요 표본을 다시 정한다. 목표 precision 또는 recall의 95% 신뢰구간 반너비가 0.10을 초과하거나, 사전에 설정한 최소 효과크기의 검정력이 0.80 미만이면 새 upstream 구현체×mutation family 그룹을 추가한다. 확대 중단 규칙은 알고리즘별 신뢰구간 반너비 0.10 이하와 검정력 0.80 이상을 모두 충족하는 것으로 사전등록한다. `not_applicable/insufficient_context`와 oracle를 통과하지 못한 mutation은 유효 성능 분모로 계수하지 않는다.

양성은 원문 규칙별로 사전 정의한 mutation operator로 생성하며, 각 mutation은 컴파일, sanitizer, 정·역함수 성질 및 해당 KAT 중 적용 가능한 oracle을 통과해 의도한 위반만 삽입되었음을 확인한다. 음성은 수정하지 않은 구현, 동치 표현, 매크로, 템플릿과 벡터화 구현을 포함한다. 전문가가 코드 주석과 mutation ID를 제거한 상태에서 occurrence GT를 확정한다.

### 7.2 분할·통계·수용 기준

- 소스 라인이 아닌 upstream 구현체×mutation family를 그룹으로 분할한다. 같은 파생 가족이 development와 test에 나뉘지 않도록 한다.
- 알고리즘별 confusion matrix, precision, recall, F1과 95% cluster-bootstrap 신뢰구간을 보고하고, 알고리즘을 동등 가중하는 macro average를 최종 일반화 지표로 사용한다.
- 개별 알고리즘 성능은 해당 알고리즘의 평가 가능 양성과 음성이 각 40건 이상일 때만 주장한다. 표본수가 부족하면 원시 수치와 신뢰구간을 탐색적으로만 보고한다.
- 수용 게이트는 평가 자료의 라이선스·commit·SHA-256 고정 100%, 생성 mutation의 컴파일 성공 100%, oracle 검증 100%, 파생 가족 분할 누출 0건, 인간 조정 GT coverage 100%로 정한다.

### 7.3 산출물

upstream lock manifest, 라이선스 목록, mutation catalog, 빌드·oracle 원장, occurrence 패킷과 GT, 분할 manifest, 알고리즘별 confusion matrix, macro/micro 지표와 신뢰구간을 생성한다.

## 8. threshold calibration

### 8.1 데이터와 분할

후보 선택 전 최신 유효 후보 265건 전체에 대해 동일한 의미의 연속 `violation_score`를 저장한다. 현재의 정수 confidence를 확률로 선언하지 않으며, 모델에게 점수를 재질문한 것만으로 독립 확률 추정값으로 간주하지 않는다. 보정 방법은 development에서 isotonic regression과 Platt scaling 중 하나를 nested group cross-validation으로 선택하고, 고정 test에 단 한 번 적용한다.

재판정 window는 development에서 사전 격자 `{55–64, 60–69, 65–74, 70–79, 75–84}`를 비교하되, 각 격자의 합집합에 포함되는 모든 occurrence에 대해 반사실적 재판정 결과를 미리 저장한다. 이로써 특정 window를 택한 뒤에 필요한 결과만 추가 호출하는 선택 편향을 차단한다.

### 8.2 통계와 수용 기준

- development에서 Brier score, ECE, calibration slope/intercept, recall·precision·F1, 재판정 추가 호출 수와 비용을 계산한다.
- 운영 목표를 먼저 고정한다. 인증 사전 검사의 우선순위를 반영하여 `violation` recall을 일차 제약으로 사용하고, development recall이 미재판정 기준보다 낮아지지 않는 선택지 중 추가 호출 수가 가장 적은 window를 선택한다. 동률이면 F1, Brier score 순으로 결정한다.
- test에서 Brier score·ECE·slope/intercept와 선택 window의 recall, precision, F1, 재판정 추가 호출 수를 95% cluster-bootstrap 신뢰구간과 함께 보고한다.
- 수용 게이트는 전체 후보 점수 coverage 100%, 사전 격자 재판정 coverage 100%, development/test `group_id` 교집합 0건, test 복도 이전 threshold/window 해시 고정과 라벨 결측 0건으로 정한다. 평가할 test 양성이 40건 미만이면 임계값 효과를 확정적으로 주장하지 않는다.

### 8.3 산출물

전체 candidate score ledger, 반사실 재판정 ledger, 그룹 분할 manifest, 보정기 파라미터, window sweep 표, reliability diagram, Brier·ECE 보고서, 고정 test 성능표를 생성한다.

## 9. 비용·실행 시간 평가

### 9.1 데이터와 반복

동결 test 코퍼스에서 L1-only, L1+L2, L1+L2+L3, L1+L3(no-RAG)를 각각 cold-cache 5회와 warm-cache 5회 실행한다. API 응답이 결정론적이더라도 지연시간은 시스템 환경에 따라 변하므로 실행 횟수를 유지한다. 실행 순서는 Latin-square로 교차하고 동일 호스트·네트워크·동시성·모델 버전을 유지한다.

### 9.2 지표·통계·수용 기준

- 소스 수, KLOC, L1 후보 수, API 호출 수를 분모로 기록한다. 단계별 wall-clock, CPU time, peak RSS, retrieval 지연, LLM 입력·출력·cache 토큰, 재시도·오류율과 estimated/actual charge를 기록한다.
- median, IQR, p95, 최대값을 보고하고, 조건 간 시간 차이는 동일 반복의 paired bootstrap 신뢰구간으로 제시한다. API 단가는 공식 가격 페이지의 조회 일시·화폐·버전과 함께 스냅샷한다.
- 수용 게이트는 요청 누락 0건, telemetry 누락 0건, 토큰 합계와 요청별 합계 일치, 단계별 시간의 전체 시간 초과 금지, cache 조건 검증 및 가격 스냅샷 해시 저장으로 정한다. 결과는 향상 임계값 없이 관찰치를 보고한다.

### 9.3 산출물

요청별 telemetry JSONL, 단계별 집계표, 시간·토큰·비용 분포, 오류·재시도 원장, 환경 manifest와 가격 스냅샷을 보존한다.

## 11. 실행 순서와 중단 조건

1. 원문 provenance catalog과 명칭 예외 규칙을 동결한다.
2. 최신 유효 스냅샷 265건의 3-view 패킷과 join sidecar를 생성하고 누출·동등성 게이트를 실행한다.
3. `minimal_cue_controlled` view를 외부 전문가 2명이 판독하고 제3자가 조정한다.
4. GT를 동결한 뒤 `group_id` development/test 분할을 동결한다.
5. development에서 점수 보정기·재판정 window·prompt·retrieval 설정을 고정한다.
6. test에서 3-view와 L2 paired 실험을 단 한 번 실행한다.
7. AES·SEED·ARIA 코퍼스를 구현체×mutation family로 동결하고 동일 프로토콜로 평가한다.
8. 비용·시간 반복 실험을 수행하고 실패와 재시도를 포함해 집계한다.
9. 모든 게이트를 독립적으로 재검증한 후에만 논문의 수치를 교체한다.

상위 단계의 해시·라벨·분할 무결성이 깨지거나 비밀 test가 조기에 개봉되면 하위 성능 결과를 폐기하고 새 스냅샷과 분할로 재시작한다. 표본수 미달은 실험 실패가 아니라 주장 범위 축소 조건으로 처리한다.
