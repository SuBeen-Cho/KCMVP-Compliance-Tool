# 공식 PDF evidence unit과 165개 활성 규칙의 누락·충돌·과잉 감사

> 이 문서의 165개·41 verified는 `CMAC-004`와 LEA 8개 원문 매핑 전의 동결 스냅샷이다. 현행 종합 수치는 166개·50 verified이며, LEA 전수 감사는 `36_LEA_53개_규칙_규범근거_전수감사.md`에서 이어진다.

## 1. 감사 목적과 범위

본 감사는 7종의 로컬 공식 PDF에서 최초 추출한 12,462개 evidence unit과 165개 활성 규칙을 대조하여, 현재 규칙의 근거 충분성과 추가 탐지 후보를 평가한다. 유료 LLM API는 사용하지 않았다. 평가는 인덱스의 원문 hash·locator·authority tier, `rule_evidence_audit.json`의 규칙별 바인딩, 활성 YAML의 적용 범위와 판정 강도를 함께 사용한다.

이 감사에서 `verified`는 원문이 규칙의 보편적 타당성을 증명한다는 뜻이 아니라, 현재 지정된 적용 범위에서 해당 원문 unit과 바인딩되었음을 뜻한다.

## 2. 165개 규칙 전수 상태

| 상태 | 규칙 수 | 해석 |
|---|---:|---|
| verified | 41 | 원문 unit, source hash, locator와 적용 범위가 봉인되어 있다. |
| review_required | 117 | 구 매핑이 있어도 해당 원문 unit과 직접 바인딩되지 않았다. |
| unmapped | 7 | 규칙을 지지하는 검증된 원문 매핑이 없다. |
| 합계 | 165 | 활성 inventory 전체이다. |

문서·시험·형상관리 규칙 중 38개는 2025.09 제출물 작성 안내서와 직접 연결되었다. 초기 승격 후보 62개 중 24개는 독립 entailment 공격감사에서 인용 span보다 주장이 강하거나 예시를 의무로 확대한 것이 확인되어 `review_required`로 롤백되었다. 반면 AES 3개, ARIA 1개, SEED 1개는 현재 7종 PDF에 해당 외부 표준 원문이 포함되지 않아 `review_required`로 남는다. LEA 세부 규칙 52개도 표준 규칙서의 수식·표·알고리즘 unit를 세분화해 개별 바인딩하기 전까지 보수적으로 `review_required`를 유지한다.

## 4. 충돌·과잉 위험

1. `DOC-KEYBIZ-SELFTEST`의 근거 표기 `§X.Y`는 실제 locator가 아니므로 지금은 활성 규범 근거로 사용하면 안 된다.
2. `TRC-001`–`TRC-004`가 지시하는 ‘2025 최신 설계 및 검증 가이드’는 현재 7종 registry의 source identity와 일치하지 않는다. 추적성 검사 기능은 유용하지만 공식 규범 위반으로 승격하기 전에 source identity를 확정해야 한다.
3. `GCM-003`, `GCM-004`, `CCM-004`, `COM-002`, `COM-005`의 정확한 함수명·반환값·버퍼 처리는 LEA 참조 소스 프로파일에서는 강한 근거이지만 모든 KCMVP 구현의 유일한 방법은 아니다. 참조 API 사용이 확인된 후보에만 profile-specific 증거로 사용해야 한다.
4. `LEA-041`, `LEA-043`의 연구·최적화 근거를 필수 규범과 동일하게 취급하면 규범 강도가 과장된다. advisory 또는 구현 방식 분류로 분리해야 한다.
5. 현재 7종 코퍼스는 KS X ISO/IEC 19790 표준 원문, NIST FIPS 197, RFC 5794, RFC 4269를 포함하지 않는다. 따라서 이를 인용한 규칙을 현 코퍼스만으로 `verified`로 승격해서는 안 된다.

## 5. 발견된 P0 인덱스·검증 결함과 수정

원문 인덱스에서 ‘무단 전재…상업적 활용 금지’ 및 Copyright footer가 매 페이지의 `requirement` unit로 생성되는 오류를 확인하였다. 이는 검색 상위를 오염시키고 규범과 무관한 문장을 공식 요구로 오인할 수 있다. 인덱서에 결정적 boilerplate 제외를 추가하고 회귀 테스트를 구성하였다. 재생성한 로컬 비공개 인덱스는 12,130개 unit이며 해당 boilerplate 잔존은 0건이다.

또한 검색 평가에서 다른 공식 문서의 distractor가 빈 applicability를 이유로 3/3 수용되고, `LEA-048`의 검증시스템 문서는 `effective_date=null`로 차단되는 반대 오류를 확인하였다. 검증기를 다음과 같이 수정하였다.

- 인용 ID가 감사 registry의 `rule_id → evidence_unit_ids → source_id/source_sha256`에 속하는지 강제한다.
- `local-artifact` 및 미발효일 문서는 문서 hash가 감사 registry의 source hash와 일치하는 content-addressed artifact인 경우에만 수용한다.
- 단순히 `local-artifact` 문자열만 있거나 hash가 다르면 `undated_artifact_provenance_unverified`로 abstain한다.

수정 후 오프라인 평가에서 relevant/oracle은 각각 3/3 수용되었고, irrelevant/conflicting은 각각 0/3 수용되었다. `LEA-048` local artifact도 원문 hash 바인딩을 통해 정상 수용되었다.

## 6. 권고 구현 순서

1. PAD-001의 적용성 픽스처를 먼저 구성하고 명시적 zero-padding 선택만 L1으로 구현한다.
2. CMAC-004는 HIGHT 64비트 예외와 bit/byte 단위 픽스처를 먼저 고정한 후 AST 규칙으로 구현한다.
3. GCM-006, CTR-006, PAD-002는 regex missing 규칙으로 추가하지 않고 상태·호출그래프·데이터흐름 증거가 있는 L3-only 파일럿으로 개발한다.
4. AES·ARIA·SEED·ISO 19790 규칙은 해당 원문을 registry에 합법적으로 포함하기 전까지 현재 `review_required`를 유지한다.
5. 모든 신규칙은 relevant/oracle > irrelevant/conflicting 검증기 조건, applicability 음성 픽스처, clone-group held-out 테스트를 통과한 후에만 활성화한다.
