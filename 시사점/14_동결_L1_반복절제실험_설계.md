# 동결 L1 기반 반복 절제 실험 설계

## 목적

현재 RAG 및 no-RAG 실행은 조건마다 L1을 다시 수행하고 임시 절대경로를 L3 입력에 포함한다. 세트별 L1 후보 수는 같았으나 후보 집합과 프롬프트 기반이 물리적으로 동일하다는 점은 입증하지 못한다. 따라서 추가 API 실행 전에 동일한 정제 소스와 L1 후보를 한 번 생성하여 동결하는 실행 경로를 구현한다.

## 불변 스냅샷

스냅샷은 다음 정보를 포함한다.

- 스키마 버전과 canonical JSON의 SHA-256으로 생성한 `snapshot_id`
- Git 커밋, workspace, 규칙, 프롬프트, 입력 파일의 SHA-256
- 정답 주석을 제거한 소스의 논리적 `source_id`, 바이트 SHA-256 및 행 수
- `세트::소스::규칙::행::발생순번`으로 구성한 안정적 후보 ID
- 절대경로를 제거한 L1 후보 payload와 payload SHA-256
- 정제 소스 트리 SHA-256 및 L3 대상 후보 ID 목록

정답 라벨은 score-only sidecar에 별도로 저장하며 L3 조건 실행에 전달하지 않는다. 정제 소스에서 `[위반: ...]` 또는 동등한 주석 표식이 발견되면 스냅샷 생성을 실패 처리한다.

## 조건 실행

RAG와 no-RAG는 각각 새로운 subprocess에서 동일한 `snapshot_id`와 동일한 후보 순서를 사용한다. 각 subprocess는 최소 환경변수만 명시적으로 설정하며 API 키를 명령행, 결과, 로그 또는 스냅샷에 저장하지 않는다. 임시 파일 경로는 프롬프트에 넣지 않고 논리적 `source_id`로 치환한다.

RAG 검색 캐시와 L3 판정 캐시는 조건 간에 공유하지 않는다. L3의 cap 및 정렬로 대상 후보가 달라지지 않도록 선택된 후보 ID 목록도 스냅샷에 고정한다.

## 요청 원장

호출별 원장은 다음을 기록한다.

- request ID와 단계(single, batch, rejudge, dual verification)
- 순서가 보존된 후보 ID 목록
- 정제 소스, 코드 문맥, RAG 문맥 및 최종 프롬프트의 SHA-256
- 응답 SHA-256, 시도 횟수, 종료 상태 및 finish reason
- 입력·출력 토큰과 실제 사용 provider/model

원격 응답 원문과 소스 원문은 기본 공개 대상에서 제외하고 해시와 비민감 집계만 공개한다.

## 반복과 분석

홀수 반복은 RAG→no-RAG, 짝수 반복은 no-RAG→RAG 순서로 수행하여 순서 효과를 교차 통제한다. 초기 반복 목표는 조건별 10회 이상이며, 관측 분산과 사전등록한 검정력 기준에 따라 확대한다. 조건은 동시에 실행하지 않아 quota 및 지연 간섭을 줄인다.

최종 scorer는 조건 실행과 분리된 프로세스에서 score-only sidecar를 결합한다. occurrence 단위와 `파일::규칙` 고유 후보 단위를 분리해 보고하며, paired bootstrap 신뢰구간과 exact McNemar 검정을 수행한다.

## 승격 게이트

다음 조건을 모두 충족해야 canonical 실험 후보로 승격한다.

1. clean tagged commit과 실행 전후 identity 일치를 확인한다.
2. 두 조건의 snapshot ID, 정제 소스 해시, 후보 ID 및 순서가 일치한다.
3. 모든 요청이 성공·실패·재시도를 포함한 원장에 기록된다.
4. skip, fallback, 누락 세트 및 라벨 누출이 없다.
5. 가격 스냅샷, 결과 SHA-256 및 로그 SHA-256을 결합한다.
6. 반복 실행과 독립 라벨링을 완료한다.
