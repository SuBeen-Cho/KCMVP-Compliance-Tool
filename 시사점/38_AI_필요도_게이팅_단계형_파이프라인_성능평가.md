# AI 필요도 게이팅 단계형 파이프라인의 성능평가 프로토콜

## 1. 연구 목적

본 평가의 목표는 AI 사용률의 최대화가 아니라, 결정적 규칙으로 판정할 수 없는 사례에만 검색과 AI를 적용하고 그 판정을 공식 근거에 구속하는 정도를 측정하는 데 있다. 단계는 `deterministic`, `retrieval`, `ai`, `abstain`으로 상호 배타적으로 기록한다. `abstain`은 실패가 아니라 근거 부족 시 확정 판정을 차단하는 안전 결과다.

## 2. 실험 단위와 재현성

동결된 데이터셋의 각 사례를 하나의 관측 단위로 삼는다. 비교 실험은 동일 사례, 동일 시스템 버전, 동일 seed, 동일 가격 스냅샷을 사용한다. 입력 계약은 `backend/evaluation/staged_pipeline_observations.schema.json`이며 모든 객체는 `additionalProperties: false`다. 하네스 자체도 동일한 폐쇄형 검증을 수행하므로 JSON Schema 라이브러리 유무와 관계없이 미정의 필드를 거부한다.

## 3. 지표 정의

- **단계 비율**: 각 단계 사례 수를 전체 사례 수로 나눈다. AI 비율을 단독 성과지표로 해석하지 않는다.
- **라우팅 전체집 분할**: 모든 사례는 `selected_deterministic`, `selected_retrieve`, `skip`, `unresolved` 중 정확히 하나에 속한다. 네 count의 합이 전체 사례 수와 같아야 한다.
- **LLM calls avoided**: 사례별 기준선 호출 수의 합에서 실제 호출 수의 합을 뺄다. 회피율은 이 차이를 기준선 호출 수로 나눈 값이다.
- **evidence coverage**: 공식 근거가 필요한 사례 중 하나 이상의 공식 근거 ID를 보유한 사례의 비율이다. 검색 성공률과 판정 정확도를 혼동하지 않는다.
- **verifier pass/abstain**: pass ratio는 검증기 적용 사례(pass+fail)만을 분모로 삼는다. abstain ratio는 최종 보류 사례를 전체로 나눈다.
- **지연시간**: 사례별 end-to-end 밀리초를 합계, 평균, nearest-rank p95로 보고한다.
- **비용**: 공급자 관측 비용의 합과, 토큰 수×동결 단가로 계산한 추정치를 분리 보고한다.

## 4. Fail-closed 불변식

AI 단계는 실제 LLM 호출을 1회 이상 기록해야 하며, 나머지 단계의 LLM 호출은 0이어야 한다. 공식 근거가 필요한데 ID가 없거나 verifier가 pass가 아닌 사례는 반드시 최종 `abstain`이어야 한다. 이 제약을 어긴 실험 파일은 지표를 생성하지 않는다.

라울 정보 부재(`route_missing`), 위조(`forged`), 실행 중 재계산과 불일치(`live_mismatch`)는 무결성 공격 게이트다. 이 경우 `route_partition=unresolved`이고 최종 결과가 `abstain`이 아니면 실험 전체를 거부한다. 공격 유형별 count와 ratio는 정상 `pass`와 분리해 보고한다.

## 5. 실행과 보고

`backend/`에서 다음과 같이 실행한다.

```bash
python -m experiments.staged_pipeline_eval observations.json -o metrics.json
pytest tests/unit/test_staged_pipeline_eval.py
```

출력의 `result_sha256`는 해시 필드를 제외한 정렬된 핵심 결과의 SHA-256다. 동일 입력과 단가로 동일한 해시를 얻어야 한다.

## 6. 해석의 한계

본 하네스는 시스템이 보고한 라우팅과 계측을 검증·집계하지만 정답 라벨에 대한 정확도를 대체하지 않는다. 따라서 성능 주장은 동결 정답집의 정확도·재현율, 근거 검색 평가, 본 운영 지표를 함께 보고해야 한다. 또한 `baseline_llm_calls`는 실측 기준선이어야 하며, 가상적 최대치를 사용할 경우 “투영치”로 명시해야 한다.
