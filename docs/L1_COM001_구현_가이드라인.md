## 1. COM 룰은 무엇을 검증하는가

### 1.1 “COM” 이라는 이름의 의미

- KCMVP 공통 요구사항(Common) 중, **구현 수준에서 자주 등장하는 보안 규칙들**을 COM-00X 형태로 묶어서 관리합니다.
- 예시:
  - **COM-001**: 잔존 정보 제거 (키·IV·평문 등 민감 데이터 사용 후 메모리에서 지우기)
  - **COM-003**: 하드코딩된 키/IV 금지
  - (추후) COM-002, COM-004 등 에러 처리, 난수 생성 등

즉, COM 룰은 “이 구현이 **기본 보안 습관**을 잘 지키고 있는지”를 자동으로 검사하는 첫 단계입니다.

### 1.2 왜 L1(COM)이 중요할까? (초보자용 직관)

- 암호 알고리즘이 아무리 안전해도,
  - 키를 코드에 박아 두거나,
  - 사용 후 메모리에 그대로 남겨 두면,
  - **메모리 덤프·로그·코어 덤프 등으로 키가 유출**될 수 있습니다.
- 그래서 COM 계열 룰은:
  - “키를 코드에 박아두지 말기”
  - “사용 후 민감 데이터는 지우기”
  - “안전하지 않은 난수 함수 쓰지 않기”
  - 같은 **기본 수칙을 기계적으로 체크**하는 역할을 합니다.

초보자 입장에서는:

> “COM은 **암호 모듈에서 꼭 지켜야 하는 생활 수칙**을 체크한다고 보면 된다”

라고 이해하면 충분합니다.

## 2. COM-001 예시로 보는 핵심 개념

### 2.1 COM-001: 잔존 정보 제거

- **규칙 ID**: `COM-001`  
- **이름**: 잔존 정보 제거  
- **의미**: 키, IV, 평문, 중간 데이터 같은 **민감한 버퍼**를 다 쓴 뒤에는,  
  `memset`, `explicit_bzero` 같은 함수로 **메모리를 덮어써서 남은 값을 제거**해야 한다.

### 2.2 “위반”과 “비위반”을 어떻게 정의할까?

- 아주 단순한 1차 기준:
  - **비위반**: 파일 어딘가에 `memset(...)` 또는 `SecureZeroMemory(...)` 같은 **잔존 정보 제거 함수 호출이 있다**.
  - **위반**: 그런 호출이 **단 한 번도 나오지 않는다**.
- 이 기준은 실제 KCMVP 심사보다 단순하지만,
  - “완벽하게 잡겠다”가 아니라
  - “명백한 미흡 케이스(완전 미구현)를 빠르게 스캔한다”는 관점에서 충분히 유용합니다.

초보자 입장에서는:

> “이 파일 안에서 memset 같은 걸 한 번도 안 썼으면, **COM-001 위반으로 찍는다**”

라고 이해하면 됩니다.

### 2.3 다른 소스 파일에서 제거하는 경우 (오탐 문제)

- 민감 데이터를 **사용하는 파일(A)** 과 **실제로 memset 등을 호출하는 파일(B)** 이 다를 수 있습니다.
  - 예: `session.c`에서 키를 쓰고, `secure_clear.c`에 정의된 `secure_clear(buf)`를 호출해 제거.
- 현재 L1은 **파일 단위**만 보므로, **A에는 패턴이 없으면** A를 COM-001 위반으로 잡습니다.
- 즉, **실제로는 제대로 제거하고 있어도** “이 파일에 memset 등이 없다”는 이유만으로 **위반(오탐)** 이 됩니다.

이 오탐을 줄이려면 아래 **§ 2.4** 구조 가이드를 참고합니다.

### 2.4 COM-001 오탐 해소를 위한 구조 가이드

**목표**: “다른 소스 파일에서만 제거하는 설계”여도, L1에서 불필요한 위반으로 잡히지 않도록 하는 구조.

| 방안 | 설명 | 구현 난이도 | 권장 |
|------|------|-------------|------|
| **A. 패턴에 래퍼 함수 이름 포함** | “이 파일에 직접 memset이 없어도, **제거용 래퍼 함수 호출**이 있으면 비위반”으로 간주. | 낮음 | ✅ 우선 적용 권장 |
| **B. 설정 가능한 제거 함수 목록** | YAML 또는 설정 파일에 `memset` + 프로젝트별 래퍼 이름 목록을 두고, 한 정규식으로 합성. | 중간 | 프로젝트별 커스터마이즈 시 |
| **C. 프로젝트/호출 그래프 수준** | “민감 데이터 사용 파일”을 식별한 뒤, 그 파일이 직접 제거하거나 **호출하는 함수**가 제거를 수행하는지까지 분석. | 높음 | 장기 개선 시 |

---

#### 방안 A: 패턴에 래퍼 함수 이름 포함 (권장)

- **의미**: “잔존 정보 제거”를 **직접 함수**(`memset`, `explicit_bzero` 등)로 하거나, **프로젝트에서 쓰기로 한 래퍼 함수**로 하면 비위반.
- **구조**:
  - `security.yaml`의 COM-001 `pattern`을 확장해, **표준 제거 함수 + 래퍼 이름**을 함께 매칭.
  - 예: `(memset|SecureZeroMemory|explicit_bzero|RtlSecureZeroMemory|secure_clear|clear_key|secure_free_key)`
  - 그러면 `session.c`에서 `secure_clear(key)`만 호출해도, 해당 파일에 `secure_clear` 문자열이 있으므로 **COM-001 비위반**으로 처리됨.
- **구현 절차**:
  1. 프로젝트/팀에서 “민감 메모리 제거용으로만 쓸 래퍼 함수 이름”을 정한다 (예: `secure_clear`, `clear_key`, `wipe_buffer`).
  2. `backend/rules/common/security.yaml`의 COM-001 `pattern`에 위 이름들을 OR(`|`)로 추가.
  3. 래퍼를 정의한 파일(예: `secure_clear.c`)에는 반드시 내부에서 `memset` 등이 호출되도록 구현·리뷰한다 (L1은 “호출 존재 여부”만 보므로, 래퍼 구현 품질은 코드 리뷰 또는 L2로 보완).
- **주의**: 래퍼 이름을 패턴에 넣으면, **그 이름을 다른 용도로 쓰는 코드**도 “제거가 있다”고 간주될 수 있음. 따라서 래퍼 이름은 **오직 잔존 정보 제거용으로만** 사용하는 것이 좋음.

---

#### 방안 B: 설정 가능한 제거 함수 목록

- **의미**: 제거 함수 목록을 YAML/설정에서 관리하고, 룰 엔진이 이 목록으로 정규식을 자동 생성.
- **구조**:
  - 예시 YAML:
    ```yaml
    - id: COM-001
      name: "잔존 정보 제거"
      pattern_type: "missing"
      # 아래 리스트로 정규식 (함수이름1|함수이름2|...) 자동 생성
      clearing_functions:
        - memset
        - SecureZeroMemory
        - explicit_bzero
        - RtlSecureZeroMemory
        - secure_clear    # 프로젝트별 래퍼
        - clear_key
      severity: high
      ...
    ```
  - `rule_engine_service.py`에서 `clearing_functions`가 있으면 `pattern` 대신 `"(" + "|".join(escaped) + ")"` 형태로 패턴을 만들어 사용.
- **장점**: 프로젝트마다 래퍼 이름만 설정에 추가하면 되고, `pattern` 정규식을 직접 수정하지 않아도 됨.

---

#### 방안 C: 프로젝트/호출 그래프 수준 (장기)

- **의미**: “이 파일이 민감 데이터를 쓰는가?”를 먼저 판별하고, 그 파일에 대해 “직접 제거 **또는** 제거를 수행하는 함수를 호출하는가?”까지 분석.
- **구조**:
  - 전제: AST/심볼 정보로 “키·IV·평문 버퍼 사용” 파일 집합과 “제거 함수 호출” 정의 위치를 파악.
  - 각 “민감 데이터 사용 파일”에 대해:  
    (1) 해당 파일 내에 표준/래퍼 제거 호출이 있으면 비위반.  
    (2) 없으면 “이 파일이 호출하는 함수들” 중 하나라도 제거를 수행하면 비위반(호출 그래프 추적).
  - 구현 시: 파서/AST, 심볼 테이블, 또는 L2(LLM) 결과를 활용하는 방식이 필요하며, 규칙 엔진 확장이 큼.
- **적용 시기**: L1을 정규식 단순 패턴에서 벗어나 “의미 단위” 검사로 확장할 때 검토.

---

**정리**: 당장 오탐만 줄이려면 **방안 A**로 COM-001 `pattern`에 팀에서 정한 **제거용 래퍼 함수 이름**을 추가하는 것을 권장한다. 프로젝트별로 래퍼 이름이 다르면 **방안 B**로 설정화하면 된다.

## 3. COM-001의 YAML 정의 해석

`backend/rules/common/security.yaml` 에 정의된 COM-001은 다음과 같습니다.

```yaml
- id: COM-001
  name: "잔존 정보 제거"
  category: common
  description: "암호 키·IV·중간 데이터 등 메모리 사용 후 명시적 제거 필요"
  pattern_type: "missing"
  pattern: "(memset|SecureZeroMemory|explicit_bzero|RtlSecureZeroMemory)"
  context: "키/IV/plaintext 버퍼 사용 직후"
  severity: high
  kcmvp_ref: "암호기술 구현안내서"
```

| 필드 | 의미 |
|------|------|
| **id** | 룰 식별자. 보고서·패치에서 COM-001로 참조. |
| **name** | 사람이 보는 규칙 이름. |
| **category** | common = 알고리즘/모드 무관 공통 룰. |
| **description** | 규칙 설명. |
| **pattern_type** | `"missing"` = **이 패턴이 없으면 위반**. (반대는 “이 패턴이 있으면 위반”) |
| **pattern** | 정규식. `memset`, `SecureZeroMemory`, `explicit_bzero`, `RtlSecureZeroMemory` 중 하나라도 나오면 “잔존 정보 제거” 호출이 있는 것으로 봄. |
| **context** | 해석용. “키/IV/plaintext 버퍼 사용 직후”에 이 패턴이 있어야 한다는 뜻. (첫 구현에서는 파일 단위로만 적용해도 됨.) |
| **severity** | high. 위반 시 보고서에 심각도 high로 표시. |
| **kcmvp_ref** | 근거 문서. 나중에 L3 RAG에서 참조. |

**pattern_type "missing"의 구현 의미**  
- 파일(또는 나중에는 함수/블록) 내용에 `pattern` 정규식에 **매칭되는 문자열이 없으면** → COM-001 위반 1건으로 기록.  
- 매칭되는 문자열이 **있으면** → 그 파일(또는 해당 영역)에 대해서는 COM-001 위반이 아님.

## 4. 초보자용 COM 룰 작성 방법 (YAML 템플릿)

### 4.1 공통적으로 기억해야 할 것

1. **id는 절대 함부로 바꾸지 말 것**
   - `COM-001`, `COM-003` 같은 ID는
     - 보고서,
     - 프론트 UI,
     - L2/L3 프롬프트,
     - 테스트 데이터  
     등 여러 곳에서 동시에 쓰입니다.
   - 새로운 룰을 추가할 땐 **새로운 ID**를 만들고, 기존 ID는 가능하면 유지하세요.

2. **패턴과 pattern_type만으로 “대략적인 필터”를 만든다**
   - COM 룰은 L1 단계라서,
     - “완벽한 판정”보다는
     - “의심되는 코드 범위를 넓게 잡는 역할”에 가깝습니다.
   - 나중에 L2(LLM), L3(RAG)에서 더 정교하게 거르기 때문에,  
     **조금 넉넉하게 잡는 쪽이 안전**합니다.

### 4.2 COM-00X YAML 템플릿 (예시)

```yaml
- id: COM-00X
  name: "룰 이름 (한글)"
  category: common
  description: "무엇을 왜 막고 싶은지 한 줄 설명"
  pattern_type: "missing"   # 또는 "regex"
  pattern: "<정규식>"       # 정규식이 어렵다면 우선 간단한 문자열 OR 패턴부터 시작
  context: "이 패턴이 필요한/위험한 상황에 대한 설명"
  severity: high            # high / medium / low 중 선택
  kcmvp_ref: "참고한 KCMVP 문서/조항"
```

#### pattern_type 종류 예시

- `"missing"`:  
  - 예: COM-001 – “memset 같은 함수 호출이 전혀 없으면 위반”.
- `"regex"`:  
  - 예: COM-003 – “`0x12, 0x34, ...` 같은 긴 16진수 배열이 있으면 위반 후보”.
- (향후) `"semantic"` 등:
  - 정규식만으로는 어렵고, L2/AST 분석이 필요한 경우에 메타 정보용으로 사용할 수 있습니다.

### 4.3 “초보자도 할 수 있는” 정규식 작성 팁

- **함수 이름 하나만 찾고 싶다**  
  - 예: `memset` 이라는 글자가 코드에 등장하는지만 확인:
  - `pattern: "memset"`

- **여러 함수 이름 중 하나라도 있으면 OK/위반으로 보고 싶다**
  - OR(`|`) 연산자 사용:
  - `pattern: "(memset|explicit_bzero|SecureZeroMemory)"`

- **긴 16진수 배열(하드코딩된 키 후보)을 찾고 싶다**
  - 예: `0x01, 0x23, 0x45, 0x67, ...` 가 8개 이상 있는 경우:
  - `pattern: "(0x[0-9a-fA-F]+\\s*,\\s*){8,}"`

정규식이 어렵다면:

- 먼저 **간단한 문자열 매칭부터** 시작하고,
- L2/Gemini로 의미를 한 번 더 확인하는 식으로 단계를 나누는 것을 권장합니다.

## 5. 룰이 코드에서 어떻게 동작하는지

이 부분은 “룰이 실제로 프로젝트 안에서 어디에 쓰이는지”를 이해하기 위한 요약입니다.

### 5.1 룰 로딩

- `backend/app/services/rule_engine_service.py` 내에서:
  - `load_ruleset(rules_dir, "common")` 으로 `security.yaml` 의 COM-00X 목록을 가져옵니다.
  - 각 룰에 대해 `pattern_type`, `pattern` 에 따라 분기합니다.

### 5.2 파일 순회 + 패턴 적용

- `preprocess_result["files"]` 에는 분석 대상 파일 목록이 있습니다.
  - 각 항목: `{ "path": "...", "ast": {...}, "lines": [...] }`
- `path` 를 이용해 파일 내용을 읽고,  
  COM-001 같은 `"missing"` 룰이면:

```python
if not regex.search(content):
    # 이 파일에는 잔존 정보 제거 호출이 없음 → COM-001 위반 1건 추가
```

COM-003 같은 `"regex"` 룰이면:

```python
for match in regex.finditer(content):
    # match 시작/끝 라인 계산 → 그 범위를 위반으로 추가
```

### 5.3 violations.json 에 기록되는 형태

룰 적용 결과는 `violations.json` 에 다음과 같은 형태로 저장됩니다.

```json
{
  "rule_id": "COM-001",
  "file": "src/session.c",
  "line": null,
  "scope": "file",
  "message": "잔존 정보 제거",
  "severity": "high",
  "snippet": "...파일 앞부분 코드..."
}
```

또는 COM-003처럼 라인 범위가 있을 때:

```json
{
  "rule_id": "COM-003",
  "file": "src/key_storage.c",
  "line": 5,
  "end_line": 8,
  "scope": "line-range",
  "message": "하드코딩된 키/IV 금지",
  "severity": "high"
}
```

프론트엔드는 이 정보를 이용해:

- 파일 트리 빨간 점,
- 코드 뷰어 하이라이트,
- 위반 목록(파일·라인·메시지)  
등을 렌더링합니다.

## 6. COM 룰 수정·추가 시 체크리스트

COM-001/003 등 **COM 룰을 수정하거나 새로 추가했을 때, 팀원이 꼭 같이 해야 하는 일**을 한 번에 정리한 표입니다.

### 6.1 룰(YAML) 수정/추가 시

- [ ] **`id`는 유지 또는 새로운 값 사용**
  - 기존 COM-001/003의 `id`를 바꾸지 않는다.
  - 새 룰은 `COM-00X`처럼 **새 ID**로 추가한다.
- [ ] `name`, `description`, `severity`, `kcmvp_ref`를 의미 있게 채웠는지 확인.
- [ ] `pattern_type`이 `missing` / `regex` 중 어떤 의미인지 이해하고 선택했는지 확인.
- [ ] `pattern`이 너무 좁지도(놓치지 않는지), 너무 넓지도(엉뚱한 것까지 잡지 않는지) 대략 감 잡기.

### 6.2 테스트 데이터 / 예제 코드

- [ ] `backend/testdata/` 에 **위반이 나와야 할 예제 C 코드** 추가.
- [ ] 필요하면 `backend/scripts/create_sample_zip_*.py` 를 수정/추가해서 ZIP 생성.
- [ ] 새 ZIP을 업로드해 `violations.json` 에 새로운 COM 룰이 예상대로 잡히는지 확인.

### 6.3 L2(Gemini)와의 연동

- [ ] 이 룰이 L2 의미 분석 대상인지 결정:
  - 예: COM-003처럼 “진짜 키인지 상수 테이블인지 구분해야 하는 룰”이라면 L2에 포함.
- [ ] `backend/app/services/llm_service.py` 의 프롬프트에서  
  - 새로운 COM-00X 규칙 설명이 필요하면 추가.
- [ ] L2에서 어떤 `rule_id` 를 처리할지 목록에 반영:
  - 예: `if v.get("rule_id") in ("COM-003", "COM-00X"):` 등.

### 6.4 RAG(L3) 연동을 고려한 작업

- [ ] `docs/RAG_연결_가이드라인.md` 에서 COM-00X가 **어느 KCMVP 조항에 대응하는지** 메모.
- [ ] 나중에 RAG 인덱스를 만들 때,  
  - 해당 COM-00X와 관련된 문단에 `rule_id: "COM-00X"` 메타데이터를 붙일 수 있도록 준비.
  - **예시 작성 방식 (택 1 또는 혼합)**:
    - (a) **JSONL 파일 형태** (예: `backend/docs/com_rules.jsonl`)
      ```json
      {"rule_id": "COM-001", "doc_title": "2025 최신 암호모듈 설계 및 검증 가이드", "section": "3.2.1", "page": 27, "text": "키, IV 등 민감 정보는 사용 후 즉시 메모리에서 제거해야 한다."}
      {"rule_id": "COM-003", "doc_title": "2025 최신 암호모듈 설계 및 검증 가이드", "section": "3.2.3", "page": 31, "text": "암호 키를 소스 코드에 하드코딩해서는 안 되며, 안전한 키 관리 모듈을 통해 주입해야 한다."}
      ```
    - (b) **마크다운 주석 + 구분선** (예: `backend/docs/com001_memset.txt`)
      ```text
      [rule_id=COM-001] [doc_title=2025 최신 암호모듈 설계 및 검증 가이드] [section=3.2.1] [page=27]
      키, IV 등 민감 정보는 사용 후 즉시 메모리에서 제거해야 한다. 이때 memset, explicit_bzero 등의 안전한 API를 사용하는 것이 권장된다.

      ---
      [rule_id=COM-001] [doc_title=2025 최신 암호모듈 설계 및 검증 가이드] [section=부록 A] [page=120]
      표 A-1. COM-001 잔존 정보 제거 체크리스트 ...
      ```
    - (c) **간단한 CSV/TSV** (나중에 파싱하기 쉬운 형태면 아무 형식이나 OK)
  - 중요한 것은:
    - `rule_id`, `doc_title`, `section`, `page`, `text` 정도의 필드를 **일관된 이름으로 항상 적어두는 것**.
    - 이렇게 해 두면 RAG 인덱스를 만들 때 이 메타데이터를 그대로 읽어서  
      “COM-001 관련 조항만 우선 검색” 같은 전략을 쉽게 적용할 수 있습니다.

## 7. 테스트 시나리오 예시

초보자가 따라 할 수 있는 수준으로, COM-001 기준 테스트 시나리오를 예로 들면 다음과 같습니다.

1. **위반이 나와야 하는 코드**
   - `memset`, `explicit_bzero`, `SecureZeroMemory` 중 아무 것도 없는 C 파일.
   - 키/IV/평문 버퍼를 선언하고 사용하지만, 사용 후 **아무 것도 하지 않는** 코드.
   - 기대: `violations.json` 에 COM-001 위반 1건 이상.

2. **위반이 나오면 안 되는 코드**
   - 위 코드에 `memset(key, 0, sizeof(key));` 한 줄만 추가.
   - 기대: 해당 파일에 대해서는 COM-001 위반이 없어야 함.

3. **end-to-end 테스트**
   - 위 두 파일을 ZIP으로 만들어 `testdata/`에 넣고,
   - 프론트에서 ZIP 업로드 → 분석 실행.
   - 파일 트리·코드 뷰어·위반 목록에서 COM-001이 예상대로 표시되는지 눈으로 확인.
