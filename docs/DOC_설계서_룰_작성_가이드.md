## 설계서용 DOC-xxx 룰 작성 가이드

이 문서는 `backend/rules/docs/design.yaml` 안에 들어가는 **설계서용 DOC-xxx 룰**을 어떻게 작성할지 정리한 간단한 가이드입니다.  
예시는 현재 구성된 룰(DOC-001, DOC-001b, DOC-002)을 기준으로 설명합니다.

---

### 1) 설계서(DOC-xxx) 룰셋 개요

- **목적**: KCMVP 설계서(기본/상세 설계서)에 **필수 섹션/표/문구가 빠지지 않았는지** 자동으로 검사하기 위함입니다.
- **대상**: 설계서 PDF를 업로드하면 전처리(`doc_preprocess_result.json`)에서 뽑힌 텍스트·표를 대상으로 검사합니다.
- **위치**: `backend/rules/docs/design.yaml`
- **전처리 요약**:
  - `doc_type: design` 으로 태깅된 설계서 파일의 `title`(파일명), `text`(본문), `tables[].name`/`tables[].headers` 를 모두 이어붙여 **풀텍스트**를 만들고,
  - 그 풀텍스트에 **missing / regex** 룰을 적용합니다.

---

### 2) 룰 전체 구조와 작성 방법

설계서용 DOC 룰은 **한 룰당 하나의 YAML 객체**로, 아래 필드들을 가집니다. 각 필드에 무엇을 넣어야 하는지 정리합니다.

#### 룰 구조 (공통)

| 필드 | 필수 여부 | 설명 · 입력 방법 |
|------|-----------|------------------|
| **id** | 필수 | 룰 고유 ID. 설계서용은 `DOC-0xx` 형식 권장 (예: DOC-001, DOC-003). 중복되지 않게 지정. |
| **doc_type** | 필수 | 적용 대상 문서 종류. 설계서는 `design` 으로 고정. |
| **name** | 필수 | 룰 이름(한글/영문). 위반 시 사용자에게 보여줄 수 있는 짧은 설명. |
| **pattern_type** | 필수 | 검사 방식. `missing` / `regex` / `ast` / `semantic` 중 하나. (타입별 설명은 §3 참고) |
| **pattern** | 조건부 | 정규식 문자열. `missing`·`regex` 일 때 필수. `ast`·`semantic` 일 때는 룰별 추가 필드와 함께 사용. |
| **severity** | 권장 | 위반 심각도. `high` / `medium` / `low` 등. | -> 그냥 자유롭게 설정
| **description** | 선택 | 룰 상세 설명. "~해야 한다", "~이 포함되면 안 된다" 등 조건을 문장으로 적기 좋음. |
| **kcmvp_ref** | 선택 | 근거 문서·절. 예: `"2025 최신 암호모듈 설계 및 검증 가이드 §3.2", 문장을 인용해도 좋음`. |

#### 작성 예시 (한 룰)

```yaml
- id: DOC-001
  doc_type: design
  name: "설계서 필수 섹션 존재 여부"
  description: "상세설계서에 '중요 보안매개변수 관리' 섹션이 포함되어야 함"
  pattern_type: "missing"
  pattern: "8\\.?\\s*중요\\s*보안매개변수\\s*관리"
  severity: medium
  kcmvp_ref: "2025 최신 암호모듈 설계 및 검증 가이드 §3.2"
```

- **id**: DOC-001 로 고유하게 부여.
- **doc_type**: 설계서만 검사하므로 `design`.
- **name**: 위반 목록에 나올 짧은 제목.
- **pattern_type**: "이 문구가 없으면 위반"이므로 `missing`.
- **pattern**: 실제로 찾을 문자열(정규식). 번호·공백 차이를 허용하려면 `\\.?`, `\\s*` 등 사용.
- **severity**, **description**, **kcmvp_ref**: 보고·근거용으로 채우면 됨.

#### design.yaml 에서의 배치

- 파일 최상단에 `# 문서 룰셋 (설계서용 DOC-xxx)` 같은 주석을 두고,
- `rules:` 아래에 위와 같은 객체를 리스트로 나열합니다.
- 새 룰을 추가할 때는 기존 `id` 와 겹치지 않게 번호를 부여하면 됩니다.

### 3) 패턴 타입 종류(총 4가지) 및 언제 쓰는지

설계서 DOC 룰에서 사용할 수 있는 **pattern_type** 은 아래 네 가지입니다. 어떤 상황에 어떤 타입을 쓰면 되는지에 집중해 정리합니다.

| pattern_type | 의미 | 언제 쓰는지 | 코드 지원 |
|--------------|------|-------------|-----------|
| **missing** | `pattern`에 매칭되는 텍스트가 **없으면** 위반 | 필수 섹션·표·문구가 있어야 할 때 | ✅ 구현됨 |
| **regex** | `pattern`에 매칭되는 텍스트가 **있으면** 위반 | 들어가면 안 되는 문구·금지 표현을 막을 때 | ✅ 구현됨 |
| **ast** | 문서/텍스트를 구조(목차·계층 등)로 해석해 조건 검사 | 섹션 번호 순서, 제목 레벨, 표 구조 등 **구조적 조건**을 보고 싶을 때 | 각자 추가 구현 필요 |
| **semantic** | 문맥·의미를 고려해 조건 검사 | "특정 섹션 안에서만 ~한 내용이 있을 때" 같은 **맥락 조건**을 보고 싶을 때 | 각자 추가 구현 필요 |

#### missing

- **의미**: `pattern` 정규식에 **매칭되는 문자열이 하나도 없으면** 위반.
- **언제 쓰나**:  
  - 필수 섹션 제목이 있어야 할 때 (예: "중요 보안매개변수 관리", "자가시험").  
  - 필수 표 이름이 있어야 할 때 (예: "인터페이스 명세표").  
  - 본문에 특정 문구/키워드가 반드시 등장해야 할 때.  
- **코드**: 이미 구현되어 있어 **바로 사용 가능**합니다.

#### regex

- **의미**: `pattern` 정규식에 **매칭되는 문자열이 하나라도 있으면** 위반.
- **언제 쓰나**:  
  - 설계서에 **들어가면 안 되는 문구**나 **금지 표현**(예: 구 버전 번호, 잘못된 알고리즘 이름)을 막고 싶을 때.  
- **코드**: 이미 구현되어 있어 **바로 사용 가능**합니다.

#### ast

- **의미**: 문서를 **구조(목차·계층·표 행/열 등)** 로 해석한 뒤, 그 구조가 조건을 만족하는지 검사.
- **언제 쓰나**:  
  - "2.2.1, 2.2.2, … 순서로 섹션이 나와야 한다", "특정 제목은 level 1이어야 한다", "표에 최소 N행이 있어야 한다" 등 **구조적 조건**을 표현하고 싶을 때.  
- **코드**: 현재 DOC 엔진에는 **ast 해석 로직이 없습니다**. 사용하려면 `doc_rule_service` 등에 **추가 코드 수정**이 필요합니다.

#### semantic

- **의미**: **문맥·의미**를 고려해 검사 (예: "어떤 섹션 안에서만", "표와 본문의 대응" 등).
- **언제 쓰나**:  
  - "8장 중요 보안매개변수 **섹션 내에서** 키 제거 절차가 서술되어 있을 때만 통과", "인터페이스 명세표 **해당 섹션**에 한해 함수 시그니처가 나열되어 있어야 함" 같은 **맥락 조건**을 표현하고 싶을 때.  
- **코드**: 현재 DOC 엔진에는 **의미/맥락 분석 로직이 없습니다**. 사용하려면 **추가 코드 수정**이 필요합니다.

### 4) 타입 적용 및 코드 미설계 부분

- **즉시 사용 가능한 타입**  
  - `missing`, `regex` 는 **코드에서 이미 지원**합니다.  
  - design.yaml 에 `pattern_type` 과 `pattern` 만 맞게 넣으면, 별도 코드 수정 없이 동작합니다.

- **새로운 타입을 만들고 싶은 경우**  
  - `ast`, `semantic` 이나 그 밖에 **새로운 pattern_type** 을 쓰고 싶다면, YAML에 이름만 넣어서는 동작하지 않습니다.  
  - **새 타입을 만드는 방법**  
    1. `doc_rule_service.py`(또는 문서 룰을 처리하는 모듈)에서 `pattern_type == "새_타입_이름"` 분기를 추가하고,  
    2. 해당 타입일 때 **어떤 데이터**(전처리 결과의 sections, tables, level 등)를 보고 **어떤 조건**으로 위반 여부를 낼지 로직을 구현한 뒤,  
    3. 필요하면 YAML에 그 타입 전용 필드(예: `required_section_order`, `min_rows`)를 정의하고, 코드에서 그 필드를 읽어 사용합니다.  
  - 이렇게 **엔진 쪽 코드를 확장해야** 새 타입이 실제로 적용됩니다.

- **ast / semantic 작성 시 pattern 과 추가 필드**  
  - **pattern 을 얼마나 디테일하게 쓸지**:  
    - `ast` / `semantic` 은 현재 DOC 엔진에서 **미구현**이므로, 지금 단계에서는 `pattern` 만으로는 동작하지 않습니다.  
    - 나중에 구현할 때를 대비해, **조건을 정규식 하나로 다 표현하기 어렵다면** `pattern` 에는 "대표 키워드나 번호" 정도만 두고, 상세 조건은 **description** 이나 **별도 필드**(예: `required_section_order`, `context: "within_section_8"`)로 문장·구조적으로 적어 두는 것이 좋습니다.  
  - **어떻게 작성해야 할지 모르겠을 때**  
    - 조건을 **문장으로 먼저 묘사**해 두세요.  
    - 예: *"8. 중요 보안매개변수 관리 섹션 내에서, 키·IV 제거 절차가 서술되어 있을 경우에만 통과"*, *"인터페이스 명세표가 있는 섹션에서, 표와 본문에 동일한 함수명이 포함될 경우"*  
    - 이렇게 **자연어 조건**을 `description` 이나 주석으로 남겨 두면, 나중에 ast/semantic 구현 시 어떤 검사를 해야 할지 정리하기 쉽습니다.

### 5) 실제 테스트 방법

#### 5.1 테스트용 설계서 파일 만들기

- 간단한 방법:
  - AI에게 \"KCMVP 설계서 예시 텍스트\"를 생성하게 해서,
  - 거기에 `8. 중요 보안매개변수 관리`, `9. 자가시험`, `인터페이스 명세표` 문구를 넣은 버전 / 일부를 뺀 버전 두 가지를 만듭니다.
  - PDF로 저장한 뒤, `design_doc` 파라미터로 업로드합니다.

#### 5.2 어떤 타입은 바로 테스트 가능한지, 어떤 타입은 코드 수정 후인지

- **바로 테스트 가능한 타입: `missing`, `regex`**  
  - 이 두 타입은 **이미 코드에서 구현**되어 있으므로,  
    - design.yaml 에 룰을 추가·수정한 뒤,  
    - 설계서 PDF를 업로드해 `/api/analyze` 를 호출하면  
  - DOC 룰이 적용되어 위반·정상 여부를 바로 확인할 수 있습니다.
  - 이 때 문서의 경우 설계서 하나만 넣어도 동작이 되지만, 코드는 필수 포함으로 로직을 구성해두었으므로, testdata에 있는 .zip파일 중 아무거나 넣어서 실행하시면 됩니다. (코드 파일 + 설계서만 넣고 분석 돌리면 됨. 다른 문서는 굳이 안 넣고 분석 돌려도 됨)

- **바로 테스트가 안 되는 타입: `ast`, `semantic`**  
  - 현재 엔진에는 **처리 로직이 없어** YAML에만 넣으면 **해당 룰은 스킵**됩니다.  
  - 도입하려면 **관련 코드 설정(구현)을 먼저 완료한 뒤** 테스트를 돌려야 정상적으로 동작합니다.  
  - 절차:  
    1. `doc_rule_service.py` 등에 `pattern_type == "ast"` / `"semantic"` 분기와 검사 로직을 구현하고,  
    2. 그에 맞는 테스트용 설계서/PDF를 준비한 다음,  
    3. 분석 API를 호출해 위반이 기대대로 나오는지 확인하면 됩니다.
    -> 따라서 직접 테스트 해보고 싶으면 코드를 돌려서 직접 테스트해봐도 좋음! 안되면 그냥 룰세만 설계해두기
