## LEA 코드 룰 작성 가이드

이 문서는 `backend/rules/algorithm/lea.yaml` 및 `backend/rules/mode/*.yaml`(CBC/CCM/CFB/CMAC/CTR/ECB/GCM/OFB)에 들어가는  
**LEA 관련 코드 룰**을 어떻게 작성할지 정리한 가이드입니다.  
구조는 `DOC_설계서_룰_작성_가이드.md` 와 동일하게 맞추되, 대상이 **코드(C 소스)** 라는 점만 다릅니다.

---

### 1) LEA 코드 룰셋 개요

- **목적**: LEA 알고리즘 및 그 운용모드(CBC, CTR, GCM 등)를 구현한 코드가  
  - 알고리즘/모드 스펙(KCMVP, 표준 문서)을 준수하는지,  
  - 위험한 사용 패턴(ECB 반복, Nonce/IV 재사용 등)을 사용하지 않는지  
  를 L1 룰(정규식 기반)으로 빠르게 검사하기 위함입니다.

- **대상 파일**:  
  - LEA 블록 암호 구현부, 키 스케줄, 운용모드(CBC/CTR/…)를 구현한 C/헤더 파일들.
  - 분석 시 API에서 `algorithm=LEA`, `mode=CBC` 와 같이 지정한 값에 따라 해당 YAML이 로드됩니다.

- **위치**:
  - 알고리즘 공통: `backend/rules/algorithm/lea.yaml`
  - 운용모드별: `backend/rules/mode/*.yaml` (cbc/ccm/cfb/cmac/ctr/ecb/gcm/ofb)

---

### 2) 룰 전체 구조와 작성 방법

코드용 LEA 룰은 공통적으로 아래 필드들을 가집니다.

#### 룰 구조 (공통)

| 필드 | 필수 여부 | 설명 · 입력 방법 |
|------|-----------|------------------|
| **id** | 필수 | 룰 고유 ID. LEA 알고리즘은 `LEA-0xx`, 모드별은 `CBC-0xx`, `CTR-0xx` 등으로 구분(예: LEA-001, GCM-002). |
| **category** | 필수 | `algorithm` 또는 `mode`. 알고리즘 공통 룰인지, 모드별 룰인지 구분. |
| **algorithm / mode** | 필수 | category에 따라 하나만 사용. `algorithm: LEA` 또는 `mode: CBC` 처럼 대상을 명시. |
| **name** | 필수 | 룰 이름(한글/영문). 위반 목록에 표시될 짧은 설명. |
| **pattern_type** | 필수 | 검사 방식. `missing` / `regex` / `ast` / `semantic` 중 하나. (타입별 설명은 §4 참고) |
| **pattern** | 조건부 | 정규식 문자열. `missing`·`regex` 일 때 필수. `ast`·`semantic` 일 때는 룰별 추가 필드와 함께 사용. |
| **severity** | 권장 | 위반 심각도. `high` / `medium` / `low` 등. |
| **description** | 선택 | 룰 상세 설명. \"~해야 한다\", \"~를 사용하면 안 된다\" 같은 문장으로 조건을 적기 좋음. |
| **kcmvp_ref** | 선택 | 근거 문서·절. 예: `\"LEA 표준 §5.1\", \"암호기술 구현안내서 §2.2.2\"`. |

#### 작성 예시 (한 룰)

```yaml (LEA의 경우)
rules:
  - id: LEA-001
    category: algorithm
    algorithm: LEA
    name: "LEA 블록 크기 준수"
    description: "LEA 구현에서 블록 크기가 128비트(16바이트)를 따르는지 검사"
    pattern_type: "regex"
    pattern: "typedef\\s+unsigned\\s+char\\s+LEA_BLOCK\\s*\\[16\\]"
    severity: medium
    kcmvp_ref: "LEA 표준 §3.1"
```

- **id**: LEA-001 로 고유하게 부여.
- **category / algorithm**: 알고리즘 공통 룰이므로 `category: algorithm`, `algorithm: LEA`.
- **name/description**: 무엇을 검사하는지 짧게/자세히 설명.
- **pattern_type**: \"이 패턴이 있으면 위반\"이므로 `regex`.
- **pattern**: 실제로 찾을 코드 패턴(정규식). 타입/이름/함수 시그니처 등을 표현.

운용모드(CBC/CTR/…) 쪽도 구조는 동일하되, `category: mode`, `mode: CBC` 처럼 대상 모드만 바뀝니다.


```yaml (운영모드의 경우)
rules:
  - id: CBC-001
    name: "CBC IV 랜덤성"
    category: mode
    mode: CBC
    description: "IV는 예측 불가능한 암호학적 난수"
    pattern_type: "semantic"
    severity: high
    kcmvp_ref: "암호기술 구현안내서"
```

### 3) YAML 파일별 역할 요약 (무엇을 적으면 되는지)

아래는 LEA 관련 코드 룰이 들어가는 YAML 파일과, **각 파일에 어떤 종류의 룰을 적으면 되는지 한 줄 요약**

| 파일 | 대상 | 여기에 적는 룰 요약 |
|------|------|----------------------|
| `algorithm/lea.yaml` | **LEA 알고리즘 자체** | LEA 블록/키 크기, 라운드 수, 키 스케줄 구현, 내부 상수 사용 등 **LEA 알고리즘 특성에 포함되는 내용**을 검사하는 룰. |
| `mode/cbc.yaml` | **LEA + CBC 모드** | 예시: LEA를 CBC 모드로 사용할 때 **IV 생성·랜덤성, IV 재사용 금지, 패딩 방식** 등 CBC 운용 규칙을 지키는지 검사하는 룰. |
| `mode/ccm.yaml` | **LEA + CCM 모드 (인증암호)** | 예시: LEA를 CCM 모드로 사용할 때 **Nonce 유일성, 태그 길이, AAD 처리** 등 인증암호 규칙을 지키는지 검사하는 룰. |
| `mode/cfb.yaml` | **LEA + CFB 모드** | 예시: LEA를 CFB 모드로 사용할 때 **피드백 크기, IV 처리, 피드백 레지스터 재사용** 등 피드백 운용 규칙을 검사하는 룰. |
| `mode/cmac.yaml` | **LEA + CMAC (메시지 인증)** | 예시: LEA 블록 암호를 CMAC에 사용할 때 **MAC 전용 키 관리, 서명/검증 API 사용 방식, 키 재사용 금지** 등을 검사하는 룰. |
| `mode/ctr.yaml` | **LEA + CTR 모드** | 예시: LEA를 CTR 모드로 사용할 때 **Nonce/카운터 유일성, 카운터 증가 방식, 블록 재사용 방지**를 검사하는 룰. |
| `mode/ecb.yaml` | **LEA + ECB 모드** | 예시: LEA를 ECB 모드로 사용할 때 **ECB 사용을 제한하거나 금지**(패턴 노출 위험)하는 룰. 예: ECB API 호출을 발견하면 경고/위반 처리. |
| `mode/gcm.yaml` | **LEA + GCM 모드 (인증암호)** | 예시: LEA를 GCM 모드로 사용할 때 **IV/Nonce 재사용 금지, 태그 검증 필수, AAD 처리** 등을 검사하는 룰. |
| `mode/ofb.yaml` | **LEA + OFB 모드** | 예시: LEA를 OFB 모드로 사용할 때 **IV/시드 재사용 금지, 동기화 방식** 등 OFB 운용 규칙을 검사하는 룰. |

요약하면:

- **lea.yaml**: \"LEA 알고리즘 자체가 표준대로 구현되었는가\"를 보는 룰.
- **각 mode YAML**: \"LEA를 해당 운용모드로 사용할 때, 그 모드별 사용 규칙을 지키는가\"를 보는 룰.

각 파일 안에서 룰을 추가할 때는 위 테이블을 참고해 **해당 알고리즘/모드에만 의미가 있는 조건들**을 넣으면 됩니다.

### 4) 패턴 타입 종류(총 4가지) 및 언제 쓰는지

코드용 LEA 룰에서 사용할 수 있는 **pattern_type** 은 아래 네 가지입니다. 어떤 상황에 어떤 타입을 쓰면 되는지에 집중해 정리합니다.


| pattern_type | 의미 | 언제 쓰는지 | 코드 지원 |
|--------------|------|-------------|-----------|
| **missing** | `pattern`에 매칭되는 텍스트가 **없으면** 위반 | 필수 섹션·표·문구가 있어야 할 때 | ✅ 구현됨 |
| **regex** | `pattern`에 매칭되는 텍스트가 **있으면** 위반 | 들어가면 안 되는 문구·금지 표현을 막을 때 | ✅ 구현됨 |
| **ast** | 문서/텍스트를 구조(목차·계층 등)로 해석해 조건 검사 | 섹션 번호 순서, 제목 레벨, 표 구조 등 **구조적 조건**을 보고 싶을 때 | 각자 추가 구현 필요 |
| **semantic** | 문맥·의미를 고려해 조건 검사 | "특정 섹션 안에서만 ~한 내용이 있을 때" 같은 **맥락 조건**을 보고 싶을 때 | 각자 추가 구현 필요 |

#### missing

- **의미**: `pattern` 정규식에 **매칭되는 문자열이 하나도 없으면** 위반.
- **언제 쓰나**:  
  - 필수 섹션 제목이 있어야 할 때 (예: "중요 보안매개변수 관리", "자가시험").  
  - 필수 표 이름이 있어야 할 때 (예: "인터페이스 명세표").  
  - 본문에 특정 문구/키워드가 반드시 등장해야 할 때.  
- **코드**: 이미 구현되어 있어 **바로 사용 가능**합니다.

#### regex

- **의미**: `pattern` 정규식에 **매칭되는 문자열이 하나라도 있으면** 위반.
- **언제 쓰나**:  
  - 설계서에 **들어가면 안 되는 문구**나 **금지 표현**(예: 구 버전 번호, 잘못된 알고리즘 이름)을 막고 싶을 때.  
- **코드**: 이미 구현되어 있어 **바로 사용 가능**합니다.

#### ast

- **의미**: 문서를 **구조(목차·계층·표 행/열 등)** 로 해석한 뒤, 그 구조가 조건을 만족하는지 검사.
- **언제 쓰나**:  
  - "2.2.1, 2.2.2, … 순서로 섹션이 나와야 한다", "특정 제목은 level 1이어야 한다", "표에 최소 N행이 있어야 한다" 등 **구조적 조건**을 표현하고 싶을 때.  
- **코드**: **ast**의 경우 룰별 추가 로직을 작성해야 함. 따라서  사용하려면 **추가 코드 수정**이 필요

#### semantic

- **의미**: **문맥·의미**를 고려해 검사 (예: "어떤 섹션 안에서만", "표와 본문의 대응" 등).
- **언제 쓰나**:  
  - "8장 중요 보안매개변수 **섹션 내에서** 키 제거 절차가 서술되어 있을 때만 통과", "인터페이스 명세표 **해당 섹션**에 한해 함수 시그니처가 나열되어 있어야 함" 같은 **맥락 조건**을 표현하고 싶을 때.  
- **코드**: **semantic**의 경우 룰별 추가 로직을 작성해야 함. 따라서  사용하려면 **추가 코드 수정**이 필요

### 5) 타입 적용 및 코드 미설계 부분


- **즉시 사용 가능한 타입**  
  - `missing`, `regex` 는 **코드에서 이미 지원**합니다.  
  - design.yaml 에 `pattern_type` 과 `pattern` 만 맞게 넣으면, 별도 코드 수정 없이 동작합니다.

- **새로운 타입을 만들고 싶은 경우**  
  - `ast`, `semantic` 이나 그 밖에 **새로운 pattern_type** 을 쓰고 싶다면, YAML에 이름만 넣어서는 동작하지 않습니다.  
  - **새 타입을 만드는 방법**  
    1. `doc_rule_service.py`(또는 문서 룰을 처리하는 모듈)에서 `pattern_type == "새_타입_이름"` 분기를 추가하고,  
    2. 해당 타입일 때 **어떤 데이터**(전처리 결과의 sections, tables, level 등)를 보고 **어떤 조건**으로 위반 여부를 낼지 로직을 구현한 뒤,  
    3. 필요하면 YAML에 그 타입 전용 필드(예: `required_section_order`, `min_rows`)를 정의하고, 코드에서 그 필드를 읽어 사용합니다.  
  - 이렇게 **엔진 쪽 코드를 확장해야** 새 타입이 실제로 적용됩니다.

- **ast / semantic 작성 시 pattern 과 추가 필드**  
  - **pattern 을 얼마나 디테일하게 쓸지**:  
    - `ast` / `semantic` 은 현재 DOC 엔진에서 **미구현**이므로, 지금 단계에서는 `pattern` 만으로는 동작하지 않습니다.  
    - 나중에 구현할 때를 대비해, **조건을 정규식 하나로 다 표현하기 어렵다면** `pattern` 에는 "대표 키워드나 번호" 정도만 두고, 상세 조건은 **description** 이나 **별도 필드**(예: `required_section_order`, `context: "within_section_8"`)로 문장·구조적으로 적어 두는 것이 좋습니다.  
  - **어떻게 작성해야 할지 모르겠을 때**  
    - 조건을 **문장으로 먼저 묘사**해 두세요.  
    - 예: *"8. 중요 보안매개변수 관리 섹션 내에서, 키·IV 제거 절차가 서술되어 있을 경우에만 통과"*, *"인터페이스 명세표가 있는 섹션에서, 표와 본문에 동일한 함수명이 포함될 경우"*  
    - 이렇게 **자연어 조건**을 `description` 이나 주석으로 남겨 두면, 나중에 ast/semantic 구현 시 어떤 검사를 해야 할지 정리하기 쉽습니다.

### 6) 실제 테스트 방법

#### 6.1 테스트용 코드 파일 만들기

- AI에게 아래와 같이 요청해 **테스트용 C 코드**를 생성하게 할 수 있습니다.\n  - 예: \"LEA-128/128 CBC 모드로 암호화/복호화하는 C 예시 코드를 만들어줘. 일부는 올바른 구현, 일부는 CBC IV를 상수로 두거나 재사용하는 잘못된 구현도 포함해줘.\"  \n- 생성된 코드를 ZIP으로 묶어 업로드하면 됩니다. 
(문서의 경우 안 넣어도 됩니다.)

#### 6.2 어떤 타입은 바로 테스트 가능한지, 어떤 타입은 코드 수정 후인지

- **바로 테스트 가능한 타입: `missing`, `regex`**  \n  - 이미 L1 코드 룰 엔진에서 구현되어 있으므로, YAML에서 이 타입만 사용하면 바로 위반/정상 여부를 확인할 수 있습니다.\n\n- **코드 수정 후 테스트해야 하는 타입: `ast`, `semantic`**  \n  - 현재 엔진에는 ast/semantic 기반 코드 분석 로직이 없기 때문에,  \n    - YAML에만 추가해 두면 분석 시 **해당 룰은 스킵**됩니다.  \n  - 도입하려면 `rule_engine_service.py` 쪽에 관련 로직을 구현한 뒤,  \n    그에 맞는 테스트용 코드(예: 잘못된 인자 개수, 잘못된 에러 처리 흐름)를 준비해서 테스트를 돌려야 정상 동작 여부를 확인할 수 있습니다.
