# [AS11.05] 형상관리시스템을 통한 형상 변경 추적 및 유지 명세

## 1. 보안요구사항 개요
형상관리 항목(개발문서, 소스파일 등)의 등록, 변경, 삭제 등 모든 이벤트 발생 시 형상관리 시스템의 로그 기능을 이용하여 이력을 남기고, 이를 통해 개정 이력을 완벽히 추적 및 유지해야 함.

## 2. 상세 요구사항 (Requirements)
- **VE11.05.01**: 형상관리시스템을 통한 식별, 등록, 개정 등 추적 필요

## 3. 작성 예시 (Examples)

### 3.1. 형상 변경 이력 관리 정책
"KISACrypto V1.0 암호모듈은 형상관리 시스템(Git/SVN)의 커밋(Commit) 및 푸시(Push) 로그 기능을 활용하여 모든 형상 변경 이력을 관리한다."

- **로그 기록 시점**: 형상관리 항목의 신규 등록, 기존 항목의 수정(개정), 불필요 항목의 삭제 시 즉시 로그를 생성함.
- **로그 포함 정보**: 작업자 식별 정보, 작업 일시(Timestamp), 변경된 파일 목록, 변경 사유(Commit Message), 이전 버전과의 차이점(Diff).
- **이력 유지**: 프로젝트 시작 시점부터 현재 버전까지의 모든 로그를 서버 내에 영구히 유지하여, 특정 시점의 모듈 상태로 복구가 가능하도록 함.

### 3.2. 변경 추적 프로세스
1. **이벤트 발생**: 개발자가 소스코드(예: `lea_core.c`) 수정 후 형상관리 시스템에 반영 요청.
2. **커밋 로그 작성**: 수정 내용과 승인 번호 등을 포함한 메시지를 작성하여 반영함.
3. **이력 추적**: 관리자는 형상관리 시스템의 `log` 또는 `blame` 기능을 통해 해당 파일의 개정 이력을 확인하고 특정 버전의 무결성을 검증함.

## 4. 구조도 및 시각 자료 (Visuals)
> **설계 핵심**: 본 항목은 형상관리 시스템이 제공하는 '로그의 불변성'과 '추적의 연속성'을 증빙하는 것이 관건임.

## 5. 해설 및 증빙 가이드 (Guide)
- **로그 기능의 활성화**: 개발 업체가 실제로 형상관리 시스템의 로그 기능을 사용하여 관리하고 있음을 증빙해야 함. 심사 시 실제 시스템의 로그 화면(Commit History)을 캡처하여 제출하는 것이 가장 확실한 증빙 방법임.
- **삭제 이력 주의**: 파일 삭제 시에도 단순히 사라지는 것이 아니라, '누가 언제 삭제했는지'에 대한 로그가 남아야 함을 명세해야 함.
- **PQC/LEA 개발 이력**: 수빈님이 진행 중인 **LEA** 최적화 과정이나 **HAETAE** 구현 중 발생한 성능 개선 및 보안 패치 이력이 형상관리 로그에 상세히 기록되어 있음을 강조할 것. 이는 개발 과정의 성숙도를 보여주는 지표가 됨.
