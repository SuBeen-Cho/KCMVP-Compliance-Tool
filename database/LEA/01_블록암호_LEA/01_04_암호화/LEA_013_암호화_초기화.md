# [LEA.013] 암호화 초기화

## 1. 보안요구사항 개요
LEA 암호화 알고리즘 1의 첫 단계로, 128비트 평문 P(바이트 배열)를 32비트 워드 배열 X₀ = (X₀[0], X₀[1], X₀[2], X₀[3])로 변환하여 초기 상태값에 대입하는 과정이다.

## 2. 상세 요구사항 (Requirements)
- **LEA-026**: 암호화 알고리즘의 첫 단계에서 128비트 평문 P를 4개의 32비트 워드 배열 X₀로 변환하여 대입해야 한다. 바이트-워드 변환은 리틀엔디언(Little-endian) 바이트 순서를 따르며, `X₀ ← P` 형태로 수행한다.

## 3. 작성 예시 (Examples)
### 3.1. 의사코드 예시

```
// 알고리즘 1 — 암호화 (첫 단계)
Input: P (128비트 평문, 바이트 배열 p[0]..p[15])
       RK_0_enc, ..., RK_(Nr-1)_enc (라운드키)
Output: C (128비트 암호문)

Step 1: X_0 ← P
  // 바이트 배열 → 워드 배열 변환
  // X_0[0] = p[0] | (p[1]<<8) | (p[2]<<16) | (p[3]<<24)
  // X_0[1] = p[4] | (p[5]<<8) | (p[6]<<16) | (p[7]<<24)
  // X_0[2] = p[8] | (p[9]<<8) | (p[10]<<16) | (p[11]<<24)
  // X_0[3] = p[12] | (p[13]<<8) | (p[14]<<16) | (p[15]<<24)
```

### 3.2. C 코드 예시

```c
void lea_encrypt(const uint8_t P[16], const uint32_t RK[][6], int Nr, uint8_t C[16]) {
    uint32_t X[4];

    // Step 1: X_0 ← P (바이트 배열 → 워드 배열)
    memcpy(X, P, 16);
    // 리틀엔디언 플랫폼에서는 memcpy로 직접 변환 가능
    // 빅엔디언 플랫폼에서는 바이트 스왑 필요

    // Step 2~4: 라운드 함수 반복 (이후 단계)
    // ...
}
```

### 3.3. 표 형식 예시 — 바이트-워드 매핑

| 워드 | 바이트 인덱스 | 리틀엔디언 변환 |
| :--- | :--- | :--- |
| X₀[0] | p[0], p[1], p[2], p[3] | `p[0] \| (p[1]<<8) \| (p[2]<<16) \| (p[3]<<24)` |
| X₀[1] | p[4], p[5], p[6], p[7] | `p[4] \| (p[5]<<8) \| (p[6]<<16) \| (p[7]<<24)` |
| X₀[2] | p[8], p[9], p[10], p[11] | `p[8] \| (p[9]<<8) \| (p[10]<<16) \| (p[11]<<24)` |
| X₀[3] | p[12], p[13], p[14], p[15] | `p[12] \| (p[13]<<8) \| (p[14]<<16) \| (p[15]<<24)` |

### 4.2. 메모리 레이아웃
평문 P의 바이트 배열 `p[0]..p[15]`가 4개의 32비트 워드로 순차 매핑된다. 리틀엔디언 아키텍처(x86 등)에서는 `memcpy(X, P, 16)` 한 줄로 변환이 완료되며, 빅엔디언 아키텍처에서는 각 워드별 바이트 순서 반전이 필요하다.

## 5. 해설 및 증빙 가이드 (Guide)
- **엔디언 처리의 중요성**: LEA 규격은 리틀엔디언 바이트 순서를 전제한다. 빅엔디언 플랫폼에서 구현 시 바이트 스왑을 누락하면 KAT 검증에서 실패하게 된다.
- **memcpy 기반 구현**: `memcpy(X, P, 16)` 형태의 구현이 가장 간결하며, 리틀엔디언 플랫폼에서는 별도 변환 없이 정확한 결과를 보장한다.
- **초기화 단계의 위치**: 이 단계는 알고리즘 1의 **1번째 줄**(X₀ ← P)에 해당하며, 라운드 함수 반복 이전에 단 한 번 수행된다.
